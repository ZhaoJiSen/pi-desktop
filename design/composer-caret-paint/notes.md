# 换行超过高度上限后的光标绘制

沿用当前 Prompt Input 视觉，只修复光标与滚动的配合；不增加动效、不删改文案、不改变 176px 输入滚动上限。

用户截图显示末行光标只剩一个点，重新点击后恢复。浏览器中的空白行、选区和滚动坐标可保持正确，但未稳定复现桌面 WebView 的点状光标，因此原生绘制原因仍是推断，不能将浏览器检查等同于原窗口复测。

## 修正

`editorDom.ts` 原先先 addRange 恢复选区，再移动 .draft-field.scrollTop。改为测量待恢复 Range、先移动滚动视口，最后 removeAllRanges/addRange 恢复原生选区。这样选择绘制使用滚动后的视口，避免光标继续沿用滚动前的裁切区域。未增加 blur/focus、异步重试或伪光标。

没有 collapsed Range 矩形的中间空白行，通过同一位置的后一个字符测量行矩形；末尾空白行继续复用现有 data-editor-tail。两者都不写入额外草稿字符。

## 检查

局部自检一轮，未独立评审。查看了浅色 Nord 下 100% 和 CSS zoom 200% 的实际截图，光标完整、工具栏与滚动条位置保持不变。

新 verify.mjs 使用 tab.pressKey(null, ...) 连续发送原生按键，不通过 locator.press() 重复指定焦点。第 11、12、13 轮连续通过：6/7/8 行高度临界点、持续到 40 行、接着输入、撤销/重做、开头编辑、刷新读回、保存失败仍保留输入、恢复后再次持久化。results.json 记录完整坐标。

旧 composer-caret-scroll 的验证脚本同步改为不重新聚焦的原生按键，所有原有断言保留；回归第 1、2、3 轮连续通过，见 regressions.json。旧的 locator 按键版本曾在开头编辑后被自动重新定位到末尾，不适合验证保持焦点的绘制问题。

200% 同一新验证通过，见 zoom-results.json。类型检查、lint、git diff --check 通过；按 skill 未运行构建或全量测试。fixture 使用真实 Composer 与隔离的浏览器草稿存储，未发送消息或连接模型。
